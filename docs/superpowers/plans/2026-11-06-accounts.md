# Comptes SAKURA (Supabase) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Comptes Discord/Google avec pseudo unique, avatar, synchro bidirectionnelle des données locales et liaison d'identités.

**Architecture:** Le store zustand (localStorage) reste la source lue par l'interface. Un moteur de synchro client fusionne avec des tables Postgres protégées par RLS : à la connexion, la version la plus récente gagne ; ensuite, les lignes modifiées partent par upsert, groupées. L'auth se fait côté navigateur avec `@supabase/supabase-js` (PKCE, session en localStorage), pour rester compatible avec un futur export statique Tauri.

**Tech Stack:** Next.js 16 (App Router, pages client), React 19, zustand 5, `@supabase/supabase-js` v2, Supabase (Postgres 17, Auth, Storage), tests avec `node --test` (types TS retirés nativement par Node 26, sans dépendance ajoutée).

**Spec:** `docs/superpowers/specs/2026-11-06-accounts-design.md`

## Global Constraints

- Projet Supabase : ref `qyebpmhhneszosykkjfj`, région eu-west-3.
- Env : `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (clé `sb_publishable_…`, jamais de clé secrète côté client).
- Pseudo : regex `^[a-z0-9_]{3,20}$`, minuscules. Mots réservés : `settings, api, auth, anime, profile, profiles, discover, search, history, watchlist, calendar, legal, onboarding, u, user, users, admin, sakura, login, logout, me, help, about`.
- Avatar : bucket `avatars`, public, 2 Mo maximum, `image/png, image/jpeg, image/webp, image/gif`. Chemin `<uid>/avatar-<timestamp>.<ext>`.
- Synchro : envoi groupé toutes les 2 s ; progression au plus toutes les 15 s, plus envoi immédiat à `visibilitychange → hidden`.
- Déconnexion : vider `watchlist`, `history`, `progress`, `deleted` du store (les réglages restent).
- Le site doit fonctionner sans compte et sans variables Supabase (client `null`, synchro inactive).
- Textes de l'interface en français.
- Next.js 16 : lire `node_modules/next/dist/docs/` pour toute API Next touchée (`useSearchParams` + Suspense, etc.).

## Review Focus

1. **Même anime supprimé sur A, puis ré-ajouté sur B** : la ligne la plus récente gagne, l'anime réapparaît. Test `merge: re-add after tombstone wins` (Task 3).
2. **Premier login avec un store local plein et un compte vide** : tout est envoyé, rien n'est perdu. Test `merge: empty remote keeps all local and marks them dirty` (Task 3).
3. **Pseudo déjà pris ou réservé, saisi en majuscules** : refusé par la base, même si le client se trompe. Test SQL dans Task 1 step 4.
4. **Second utilisateur qui tente de lire ou modifier les lignes du premier** : 0 ligne visible, insertion refusée. Test SQL dans Task 1 step 4.
5. **Délier la dernière identité** : bouton désactivé. Supabase le refuse aussi ; l'erreur s'affiche en français (Task 6).

**Interfaces:**

  - `HistoryEntry` utilise `watchedAt` comme horodatage.
  - L'état gagne :
    - `deleted: Record<string, number>` (clés `w:<animeId>` / `h:<animeId>` → horodatage de suppression),
    - `settingsUpdatedAt: number`,
    - `replaceAll(data: SyncSnapshot): void`,

  - Dans `merge.ts` (sans import `@/`, pour que `node --test` le charge) :
    - `type Row<T> = { key: string; value: T | null; updatedAt: number }` (`value: null` = supprimé),
    - `mergeRows<T>(local: Row<T>[], remote: Row<T>[]): { merged: Row<T>[]; toPush: Row<T>[] }`,
    - règle : `updatedAt` le plus grand gagne ; à égalité, la version distante gagne ; `toPush` = les lignes où la version locale a strictement gagné ou n'existe pas à distance.

  - `merge: re-add after tombstone wins` → local `{value:null, updatedAt:10}`, distant `{value:X, updatedAt:20}` → `merged` contient X.
  - `merge: tombstone newer than remote deletes` → `merged` `value:null`, `toPush` contient la tombe.
